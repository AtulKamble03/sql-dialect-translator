# SQL Dialect Translator — Requirements Document

## Overview

A C# CLI tool that scans a folder or repository for `.sql` files,
detects whether each file is written in SQL Server (T-SQL) or PostgreSQL dialect,
and uses the Claude AI API to produce a fully restructured translation in the opposite dialect.

Output is two clean folders — one containing all files translated to SQL Server syntax,
one containing all files translated to PostgreSQL syntax.

---

## Goal

Enable a development team to migrate a database between SQL Server and PostgreSQL
(or vice versa) without manually rewriting every `.sql` file.
The tool handles complete query restructuring — not just keyword replacement.

---

## In Scope

- Scan any local folder or git repo recursively for `.sql` files
- Detect source dialect: SQL Server (T-SQL) or PostgreSQL (PL/pgSQL)
- Translate using Claude AI — full restructuring, not find/replace
- Handle all SQL types: DDL (CREATE, ALTER, DROP) and DML (SELECT, INSERT, UPDATE, DELETE)
- Handle stored procedures, functions, views, indexes, triggers
- Output two folders: `/output/mssql/` and `/output/postgresql/`
- Same filename as input, placed in the appropriate output folder
- Batch processing: handle 50+ files efficiently using Anthropic Batch API
- CLI interface with configurable input/output paths

## Out of Scope (for now)

- Scanning application code files (`.cs`, `.py`, `.java`) for embedded SQL
- GUI / Windows UI
- Auto-detecting SQL in string literals inside code files
- Runtime query interception or proxy
- Configuration-based dialect switching at runtime
- Database connection or execution — translation only, no execution

---

## Functional Requirements

### FR-01 — Folder Scanning
- Accept an input folder path via CLI argument
- Recursively scan all subdirectories
- Collect all files with `.sql` extension
- Ignore non-`.sql` files silently

### FR-02 — Dialect Detection
- Analyse each `.sql` file to determine source dialect
- Detection based on keyword fingerprints (see Design doc)
- Output: `SqlServer` or `PostgreSQL` per file
- If dialect is ambiguous, default to SQL Server and log a warning

### FR-03 — Translation via Claude API
- Send file content to Claude API with a structured prompt
- Request full restructuring — not find/replace
- Receive two outputs per file: SQL Server version + PostgreSQL version
- Handle API errors with retry (max 3 attempts)

### FR-04 — Batch Processing
- For 10 or fewer files: sequential API calls
- For 11+ files: use Anthropic Message Batches API
- Poll batch status until complete
- Write results as they complete (do not wait for all)

### FR-05 — Output Generation
- Create output directory if it does not exist
- Write `/output/mssql/<original_filename>.sql`
- Write `/output/postgresql/<original_filename>.sql`
- Prepend each output file with a header comment:
  ```sql
  -- Generated by SQL Dialect Translator
  -- Source file: <original path>
  -- Source dialect: <detected dialect>
  -- Translated to: <target dialect>
  -- Generated at: <timestamp>
  ```

### FR-06 — CLI Interface
```
SqlTranslator.exe [options]

Options:
  --input   <path>   Path to folder or repo to scan (required)
  --output  <path>   Path to output directory (default: ./output)
  --dry-run          Detect and list files without translating
  --help             Show help
```

### FR-07 — Logging
- Console output: file found, dialect detected, translation started, translation complete
- Error output: API failures, unreadable files, ambiguous dialects
- Summary at end: total files, success count, failure count

---

## Non-Functional Requirements

### NFR-01 — Accuracy
- Translation must be semantically equivalent (same result, different syntax)
- Claude model: claude-sonnet-4-6 or latest capable model
- Prompt must instruct Claude to preserve all logic, aliases, column names, and comments

### NFR-02 — Performance
- Batch API for 11+ files — translate all files concurrently
- Total translation time for 50 files: target under 3 minutes

### NFR-03 — Reliability
- Retry failed API calls (max 3 attempts, 5 second backoff)
- If a file fails after retries: write error marker file, continue with remaining files
- Never crash on a single file failure

### NFR-04 — Maintainability
- Clean separation: Scanner, Detector, Translator, Writer as separate classes
- All Claude prompts in a single `Prompts.cs` file — easy to update without touching logic

### NFR-05 — Portability
- Target: .NET 10, runs on Windows
- Single executable deployment (`dotnet publish --self-contained`)

## Key Translation Patterns

These are examples. Claude handles the full translation — this table is for reference.

| Concept | SQL Server (T-SQL) | PostgreSQL |
|---|---|---|
| Limit rows | `SELECT TOP 10 ...` | `SELECT ... LIMIT 10` |
| Current timestamp | `GETDATE()` | `NOW()` |
| Null replacement | `ISNULL(x, y)` | `COALESCE(x, y)` |
| Auto-increment | `INT IDENTITY(1,1)` | `SERIAL` or `GENERATED ALWAYS AS IDENTITY` |
| String type | `NVARCHAR(100)` | `VARCHAR(100)` |
| Boolean type | `BIT` (0/1) | `BOOLEAN` (true/false) |
| Object quoting | `[table_name]` | `"table_name"` |
| Type casting | `CAST(x AS INT)` or `CONVERT(INT, x)` | `x::INTEGER` |
| If-null shorthand | `x ?? y` (not in SQL) `ISNULL(x,y)` | `COALESCE(x, y)` |
| Conditional | `IIF(cond, a, b)` | `CASE WHEN cond THEN a ELSE b END` |
| Pagination | `OFFSET x ROWS FETCH NEXT y ROWS ONLY` | `LIMIT y OFFSET x` |
| String concat | `+` operator | `\|\|` operator |
| Temp tables | `#temp_table` | `TEMP TABLE` or CTE |
| Date parts | `DATEPART(year, col)` | `EXTRACT(YEAR FROM col)` |
| Row number | `ROW_NUMBER() OVER (...)` | Same (compatible) |
| Return from INSERT | Not native | `RETURNING id` |
| Batch separator | `GO` | Not used (remove) |
| Print debug | `PRINT 'msg'` | `RAISE NOTICE 'msg'` |
| Error handling | `TRY...CATCH` | `BEGIN...EXCEPTION` |
| Stored procedure | `CREATE PROCEDURE` | `CREATE FUNCTION` (returns void or table) |

## Input / Output Specification

### Input
```
/my-repo/
  schema/
    create_tables.sql        ← DDL
    add_indexes.sql
  migrations/
    v1_add_column.sql
  stored-procedures/
    usp_get_customer.sql     ← stored procedure
```

### Output
```
/output/
  mssql/
    create_tables.sql        ← SQL Server version
    add_indexes.sql
    v1_add_column.sql
    usp_get_customer.sql
  postgresql/
    create_tables.sql        ← PostgreSQL version
    add_indexes.sql
    v1_add_column.sql
    usp_get_customer.sql
```

Note: Output folder structure is flat (all files in one level) — subdirectory structure from input is not preserved in v1.
